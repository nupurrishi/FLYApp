# FLYApp

FLYApp is a self-hosted event operations app for Fly Showcase fashion events. The application uses TanStack Start/React, Better Auth, PostgreSQL, a persistent local upload volume, Docker Compose, and Caddy for HTTPS. The intended app address is `https://app.flyshowcase.com`; this repository does not change or deploy the existing `flyshowcase.com` website.

## Current service architecture

- Node.js 22 runs the TanStack Start server build generated by Nitro.
- PostgreSQL stores Better Auth accounts/sessions and FLYApp event records. FLYApp records use an additive JSONB table to preserve the app's existing entity-oriented functions while moving persistence off Base44.
- Images are stored on the `uploaded_files` Docker volume. Image requests are authenticated and checked against the owner or event membership.
- SMTP is required for email verification and password reset. It can be a client-controlled SMTP relay; credentials belong only in the server `.env`.
- Caddy terminates HTTPS for `app.flyshowcase.com`. The DNS record and host firewall must be configured by the domain/hosting account owner.

The repo previously explored Google Sheets, WordPress/MySQL, and Supabase in other branches. They are not part of this deployment. No Base44 workspace or export was available during this migration, so no hosted records or uploaded media have been copied. Export and review any needed Base44 records before cutover; do not point production users at an empty database until the client has approved the migration plan.

## Requirements

- Docker Engine and Docker Compose plugin on a Linux server.
- Node.js 22 for local development and command-line scripts.
- A server with a public IP and inbound TCP 80/443; restrict SSH to trusted operators.
- DNS control for `flyshowcase.com`, to add `app` A/AAAA records to that server when launch is approved.
- SMTP service and credentials for `no-reply@flyshowcase.com` (or another verified sender domain).

Costs depend on the chosen server, domain/DNS provider, SMTP service, backups, and monitoring. This repo does not select or purchase a provider.

## Local development

1. Install Node.js 22 and pnpm (`corepack enable`).
2. Copy `.env.example` to `.env`. For a local standalone database set `DATABASE_URL=postgres://...@localhost:5432/flyapp`, `BETTER_AUTH_URL=http://localhost:5173`, a random secret with 32+ characters, and SMTP settings. For local Docker, create a separate `.env` with `POSTGRES_PASSWORD`, `DATABASE_URL` using host `db`, and appropriate localhost auth URL.
3. Install packages: `pnpm install`.
4. Start PostgreSQL locally or run `docker compose up -d db`.
5. Apply schema: `pnpm db:migrate` (additive `CREATE ... IF NOT EXISTS`, never resets or clears existing tables).
6. Start the app: `pnpm dev`.

Registration requires email verification. Without SMTP the app intentionally will not allow production startup; local feature work can use a local SMTP sink such as Mailpit. Never use production accounts or data for destructive testing.

## Database, backups, and admin access

`pnpm db:migrate` first runs Better Auth's schema migrations and then applies `migrations/0001_flyapp.sql`. Back up before every upgrade. On a running Compose host, a PostgreSQL logical backup can be captured with:

```sh
docker compose exec -T db pg_dump -U flyapp -d flyapp --format=custom > flyapp-$(date +%F).dump
```

Keep backups encrypted and off-host. Test restores on a separate database. The database volume and uploaded image volume both need backup/restore; the SQL dump does not contain uploaded image files. Preserve old Base44 exports until the client verifies migrated records and images.

For the initial administrator, first register normally and verify the account via email. On the trusted server shell, run `pnpm admin:create verified-account@example.com` (or `docker compose exec app node scripts/create-admin.mjs email`). It promotes one verified account only when no administrator exists. It cannot be called through the public app. Additional admins are assigned by an existing administrator through FLYApp's user management.

## Test and build

```sh
pnpm lint
pnpm test
pnpm build
```

These checks cover source linting, unit tests, and a production compilation. They do not prove live SMTP delivery, a real PostgreSQL deployment, external DNS, backups, or host firewall/TLS setup; verify those after installing the server configuration in a non-production environment.

## Production deployment

1. Provision and secure a Linux server. Install Docker + Compose. Configure firewall rules for 80/443 and trusted SSH.
2. In the domain DNS account, create `app.flyshowcase.com` pointing to the server. Keep the apex website record unchanged. Wait for DNS resolution before starting Caddy.
3. Copy the repository to the server and create `.env` from `.env.example`. Set a unique hex password for `POSTGRES_PASSWORD` (`openssl rand -hex 32`), a `BETTER_AUTH_SECRET` (`openssl rand -base64 48`), `BETTER_AUTH_URL=https://app.flyshowcase.com`, and SMTP credentials. Restrict `.env` to the deployment operator (`chmod 600 .env`). Do not commit it.
4. Run `docker compose build` and `docker compose up -d db`.
5. Run the schema migration once: `docker compose run --rm app node scripts/migrate.mjs`.
6. Start the app and HTTPS proxy: `docker compose up -d`.
7. Create the first administrator as described above; verify sign-in, password reset, event data, uploads, health/availability, and automatic HTTPS.
8. Configure scheduled encrypted backups for PostgreSQL and `uploaded_files`; verify restoration before inviting event participants.

Use a reviewed commit/tag for each upgrade. Back up database and uploads, pull/build, run migration, then restart. `compose.yaml` uses named volumes and does not publish PostgreSQL to the public network. No deployment, DNS, server, production data, or account changes were made by this repository work.

## Access model

All non-admin access requires a verified signed-in user and an active membership in that event. Event records are looked up and checked before operations. Roles live on event memberships; `admin` is a separate protected global Better Auth field.

| Role | Read | Create / update | Delete | Scope |
| --- | --- | --- | --- | --- |
| Model | Event schedule items visible to all/models or assigned to them; event announcements, looks/segments, own look and hair/makeup assignments, own readiness tasks, opportunities, own applications/profile | Own profile; own assignment status; own readiness completion; submit an application once per opportunity | None in event operations | Only active memberships; own private profile/application details and assignments; event audience rules apply |
| Designer | Event workspace, collections, own looks, look assignments, designer profile | Own designer profile, collections and looks; assign eligible event models to own looks; update own assignments | Own collections, looks, and look assignments | Active member events and records verified against designer ownership |
| Stage Manager | Full schedule, show segments, run-of-show and stage operations for their event | Schedule, segment, show status, advance/reset operations | Event schedule items and show segments | Only event(s) with stage-manager membership |
| Backstage Manager | Event team and backstage operations, model readiness and assignments | Hair/makeup appointments/stations, readiness tasks, assignment management, event announcements | Hair/makeup appointments and readiness tasks | Only event(s) with backstage-manager membership |
| Admin | User summaries, events, memberships, applications, audit records, and all event workspaces | Create/update events, assign event roles, manage opportunities/applications, and perform event/admin operations | Delete events/memberships/opportunities and linked records | Cross-event access; user role is never self-editable or supplied through public registration |

The backend checks session, membership, event ownership, and role in every server function and file route; frontend visibility is only a usability layer. Audit records are created for important administrative and show-control actions. Review the specific server handler before changing a role's access or adding a new workflow.

## Client handoff and limitations

- Client owns the server, DNS, PostgreSQL backups, SMTP account, and FLYApp database contents.
- Domain launch requires an operator to create DNS and configure the host; this repository assumes `app.flyshowcase.com` but has not changed DNS.
- Importing data requires authorized exports from the prior platform and a field mapping review. No Base44 credentials or records were available to validate or migrate.
- Accounts must verify email; SMTP is required. There is no OAuth/social sign-in in the self-hosted build.
- Email delivery is sent synchronously; a production mail relay should be monitored and deliverability verified.
- Current event records are JSONB-backed for compatibility with existing application code. Future schema/reporting needs may warrant normalized tables and a reviewed data migration.
- There is no configured automated backup scheduler, monitoring/alert service, or external object storage. The client must configure and test these operational services before launch.
- Automated checks and their actual results are recorded in the release handoff; external account and deployed-host checks remain separate.
